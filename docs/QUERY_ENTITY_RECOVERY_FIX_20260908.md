# 系统用户查询定位与错误修复

## 已确认的故障

2026-09-08 的问数审计 145 使用已发布 v14。模型将同一系统 ID 依次用于团队主键、用户主键、团队管理员和产品团队字段，四次查询为空；随后未核对 alpha_office 物理字段就查询不存在的 office_name，耗尽 5 次额度。

同一问题在 2026-09-04 审计 129 已用 alpha_user.alp_office_id 查询成功，返回 16 行。当前再次通过只读 SQL 核对，该 ID 对应用户给出的完整系统名，四个要求字段仍返回 16 行。v9 与 v14 中所需物理映射均存在；没有证据说明字段丢失导致本次故障。

此前本体构建验收侧重结构和关系覆盖，未涵盖这条历史问数的模型行为回归。本次补充该行为验证；历史成功 SQL 不直接写入线上已审核的发布评测集。

## 最小完整修改

- 运行时提示与 Claude 查询契约一致要求用机构/团队名称和 ID 联合定位。团队字样不决定 ID 类型；已存在机构名称和 ID 的目标明细可直接筛选。
- 字段物理名称不确定时读取结构，不搬用其他表的同义字段。一次定位为空后结合其他线索调整。
- SQL 工具返回当前剩余额度，连续空结果提供纠正方向，不把空定位推断为没有数据。
- 将数据库明确的 1054、1146、1052 错误区分为表列问题，返回该次查询涉及的目录结构供修正。数据库模式每个请求最多补偿两次此类错误；正常空结果、扫描超限、超时及策略拒绝仍消耗原额度。
- 不增加成功查询的原额度、不引入本体表列或关系白名单，也不要求每条合法 SQL 必须先读结构。只读、数据源边界、扫描上限、结果凭据继续生效。
