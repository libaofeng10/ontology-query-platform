# 问数 Loop V2 全面优化实施方案

> 状态：P0–P2 已实施；P3 就绪检查与灰度分桶已实施，正式 Gold 仍待业务审核与补齐  
> 开始日期：2026-08-18  
> 目标问题：避免实体被拆词或改写、跨表借用同名枚举、重复无效调用、部分结果冒充完整结果，并让每次失败可归因、可评测、可回滚。

## 1. 目标架构

```text
用户问题
  → QueryIntent（保留原文实体、时间、对象、产品和完整范围）
  → 意图增强检索（知识页 + 表字段 + 会话 + 向量）
  → 实体/字段解析
  → Query Plan
  → 确定性 SQL Guard
  → EXPLAIN + 只读执行
  → 范围与 LIMIT 完整性检查
  → 汇总、证据与审计
```

Loop 生命周期统一为 `UNDERSTAND → RETRIEVE → RESOLVE → PLAN → VALIDATE → EXECUTE → REPAIR → SUBMIT`。模型负责提出动作，Harness 负责状态、权限、预算、去重、校验、执行和终止。

## 2. 分阶段实施

### P0｜正确性止血（已实施）

- 新增 `QueryIntent v1.1`，固定用户原句中的实体、时间范围、查询对象、显式产品和 exhaustive 范围；业务对象统一覆盖线索、账号、客户、订单、案件和收入。
- 支持无“律所”后缀的高置信机构短语，例如“北京大成本月进线的线索”中的 `北京大成`；“北京地区”仍按区域理解。
- 实体和时间约束在 SQL 执行前做确定性完整性检查；机构实体不得改成 `city='北京市'`，也不得拆成两个 `LIKE`。
- 修复 SQL Guard 字段归属：未限定字段只在当前 SELECT 的物理表范围内解析；多表同名字段必须加表别名。
- 枚举字典只按准确的 `table.column` 归属匹配，不再从其他表借用同名字段字典。
- 区分枚举模式：显式数组视为 `closed`；发现探针产生的 `ds_enum` 视为 `observed`，仅作证据，不把未采样值当非法值。
- 相同工具 + 相同参数的动作第二次调用直接返回 `REPEATED_ACTION`，不再消耗 SQL 执行与扫描预算；连续两次重复触发 `REPEATED_ACTION_LIMIT` 无进展熔断。
- 工具错误统一携带 `stage`、`code`、`retryable`、`failureClass` 和可选 `details`。

### P1｜编排、检索与完整性（核心已实施）

- QueryIntent 按业务对象、实体、时间、显式产品和完整范围生成结构化检索分面及同义词，不把任一具体物理表名写死在意图规则中。
- 检索结果增加页面、表候选分数与最终选中范围，写入审计，不记录向量或采样行。
- 检索由单一总分榜升级为“分面独立配额 → 知识页绑定 → 全局结构补召回 → 已确认关系扩展”；业务对象候选先占保留配额，强势的机构、时间或通用知识页不能再把事实对象挤出上下文。
- 每次检索产生 `coverageContract`，记录必需分面、已覆盖分面和缺失分面；目录没有对应能力时在规划前以 `schema_gap` 拒绝，不允许拿其他对象的表替代。检索轨迹标记 `retrieval-v2.2`。
- SQL 执行前增加 `INTENT_SUBJECT_DROPPED` 校验，要求物理表命中至少一个业务对象分面；多对象问题在提交时还须覆盖全部对象分面，否则返回 `INTENT_SUBJECT_INCOMPLETE`。
- 会话历史只扩展检索召回，不再被直接解析成本轮不可变意图，避免上轮提到的产品、机构或对象污染当前追问。
- `search_context` 成功后从下一轮工具白名单移除，强制状态从检索推进到结构、实体或规划阶段，避免模型在已取得相同上下文后继续空转。
- 新增 `resolve_entity` 工具：返回不可变实体值和候选机构字段，不能查询、改写或拆分实体。
- 工具轨迹记录生命周期 phase；`run_sql` 明确经过 `PLAN → VALIDATE → EXECUTE`。
- 结果集记录安全 LIMIT；返回行数达到 LIMIT 时标记 `mayBeTruncated`。用户要求“所有/全部/完整”时，可能截断的结果不得作为完整答案提交或预算兜底。
- 多账号体系继续按结果集聚合，必须覆盖所有账号主表和产品维度。

### P2｜可观测性与门禁（代码已实施，真实数据待执行）

- `ds_audit` 新增：`intent_version`、`intent_json`、`prompt_version`、`retrieval_trace_json`、`failure_class`。
- 失败分类统一为：
  - `intent_error`
  - `retrieval_miss`
  - `schema_gap`
  - `guard_false_positive`
  - `policy_block`
  - `data_quality`
  - `execution_error`
  - `budget_exhausted`
  - `result_incomplete`
- Agent 评测门禁新增重复动作、意图错误和结果不完整计数；重复动作率默认不得超过 10%。
- Prompt 使用 `query-loop-v2.2` 版本标识；提示词正文仍由设置中心“提示词”独立 Tab 管理，安全工具协议和确定性护栏不可被自定义模板关闭。

### P3｜生产灰度（待目标环境执行）

1. 补齐正式 Gold 集，至少覆盖：实体 + 时间、同名字段、跨产品全集、零结果、超 LIMIT、多表 JOIN、短追问。
2. `off` 与 `required` 对照运行，记录结果等价率、P95、token、工具成功率、澄清率、预算兜底率和重复动作率。
3. 门禁通过后只切换到 `prefer`，先 10% 查询流量，再 30%，最后全量；任何关键指标回退立即恢复 `off`。
4. Prompt 变更采用“草稿 → 回归 → 门禁 → 发布”，保留上一版本以便回滚。

## 3. 关键验收场景

除下列生产关键场景外，自动化矩阵还覆盖线索、账号、客户、订单、案件、收入六类对象，并验证强语义干扰页不能挤掉目标事实表、无目标能力时覆盖契约必须报缺失、SQL 使用无关表时必须在执行前拦截。

### 场景 A：北京大成所有账号

输入：`查询一下北京大成律所所有账号情况`

- QueryIntent 实体必须是 `北京大成`，范围必须是 exhaustive。
- Alpha 与 AlphaGPT 账号主表均须覆盖。
- 两套结果分别保留，不允许预算结束只返回最后一条 SQL。
- 机构条件必须连续匹配 `北京大成`，不能拆词。
- 存在产品字段的账号主表必须返回产品维度。

### 场景 B：北京大成本月进线线索

输入：`查询一下北京大成本月进线的线索`

- QueryIntent：机构 `北京大成`、对象 `clue`、时间 `current_month`。
- 正确过滤方向是机构名称字段 + 线索进线时间字段。
- 不得退化为 `city='北京市'`。
- `alpha_crm_clue.city` 没有字典时，不得借用其他表的 `city` 字典产生误拦截。

## 4. 发布与回滚

- 默认 `QUERY_AGENT_MODE` 不因代码完成自动调整；真实 Agent Gate 返回 `enable_agent_prefer` 前保持当前配置。
- 数据库变更均为追加列，可兼容旧审计记录。
- QueryIntent 和 Prompt 都带版本；发生回归时可按版本定位。
- 回滚优先顺序：切回 `off` → 恢复上一 Prompt → 回退 Loop V2 代码；SQL 只读与 AST 护栏始终保留。
