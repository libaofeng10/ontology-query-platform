# 本体结果：面向业务用户的精简方案

日期：2026-09-07。状态：首版已实施，发布验收记录见文末。本文配套交互示意使用示例数据，不连接线上服务。

## 1. 目标与判断

让用户只做三类事情：选择哪些数据参与问数、查看系统理解的业务含义、在确有歧义时补一句说明。用户不需要学习候选、业务域批次、草稿合并、Schema、评分路由和发布门禁。

当前复杂度来自流程职责拆散：后台完成生成后停止，用户在生成工作台完成确认和合并，再进入版本编辑器校验、评测和发布。仅隐藏按钮会把这条链路留在原地，用户仍然无法直接使用结果。

截图已经显示“合并草稿已创建”、待审核为 0，却继续展示人工审核队列和 184 个生成批次。这些信息适合诊断历史任务，不适合作为业务用户的当前工作入口。

建议主线：**选表 → 自动整理与检查 → 开始问数**。模型负责理解和修正，平台负责可靠地执行整个流程，用户提供模型无法从证据中确定的业务事实。

## 2. 页面只保留一个本体结果工作区

保留外层“数据源与本体”的定位及数据表、关系与枚举、连接设置能力。本次重点取消本体结果内部的三个并列工作模式。

| 现有功能 | 新位置与行为 |
| --- | --- |
| 本体结果 | 默认工作区，优先展示当前已用于问数的版本与可用范围 |
| 生成记录与确认 | 自动整理过程可按需展开；只把尚需业务判断的问题带回主页面 |
| 人工审核队列 | 改为“需要补充的说明”；同一问题合并，模型先补证据并尝试修正 |
| 生成批次、全域发布单、分域列表 | 收入更新记录的执行详情；按一次用户发起的更新聚合，不把子批次平铺 |
| 预览、合并草稿、保存、校验、常规发布 | 由持久化后台任务连续完成，不再要求用户切换页面接力 |
| 高级编辑与历史 | 拆成“更新记录”和管理员的“专家工具”，从“更多”进入 |
| 对象/字段修改 | 在结果详情中直接修改业务名称、说明，或用一句话请求 AI 修正 |
| 模型调用留痕、Token、原始响应、JSON、分数明细 | 保留在诊断详情与专家工具中，不占据默认首屏 |

首屏仅有三块内容：

1. **当前状态与下一步**：是否可问数、本次更新进展，以及一个主操作。
2. **业务对象列表**：业务名称、一句话含义、相关对象。搜索保留；展开后才显示字段与来源表。
3. **需要说明的问题**：仅在模型仍无法判断时出现。没有问题就不显示空队列。

已有可用版本时，进入页面直接展示可用结果。本次更新、旧版本及历史生成任务分别归属自己的记录，旧批次的 review 模式不再显示成当前生效策略。

## 3. 操作与状态

| 场景 | 用户看到什么 | 主操作 |
| --- | --- | --- |
| 首次使用 | 选择用于问数的数据；不出现空的版本编辑器 | 选择数据表 |
| 正在整理 | 读取结构、整理业务含义、检查并启用的进展；可离开页面 | 无需接力操作 |
| 已可问数 | 当前业务对象和关联，最近一次更新摘要 | 开始问数 |
| 本次更新有业务歧义 | 具体问题、已知依据、受影响范围；已有版本仍可问数 | 补充说明 |
| 系统问题导致未完成 | 聚合原因、已保留的进度、适合当前身份的下一步 | 重试未完成部分，或管理员检查配置 |
| 更新会改变既有口径 | 一份业务语言的变化摘要与影响范围 | 确认这次变化 |

“当前是否可用”和“本次更新是否完成”独立表达。例如：当前结果可用于问数；本次更新还有 1 处需要说明。不能因为新任务失败就把已有结果显示为不可用，也不能把生成成功、已创建草稿显示为已经生效。

更新记录按用户的一次操作展示，例如“新增 3 个业务对象，补充 2 处说明”；展开才看到各域、批次与调用记录。恢复旧版本先检查当前物理结构是否仍兼容，并明确其影响。

## 4. 自动处理的边界

### 模型处理

- 结合当前选表范围、结构、字段注释、已登记知识以及已启用的样本画像，生成名称、属性说明与关系建议。
- 对低分或冲突项先查已有知识、补读所需结构，再提出修正；修正后重新由同一评分与校验流程判断。
- 合并含义相同、物理映射一致的重复候选；已有人工定义作为明确依据，不能被新生成内容悄悄覆盖。
- 将同一原因的多条问题汇成业务语言的问题，只请求一次必要说明。
- 接收“把这个字段解释改成……”等自然语言修正，形成变更并说明影响。

### 平台自动执行

- 保存选表范围、读取数据、分批、评分、合并、结构校验、必要评测、版本切换及过程留痕。
- 继续使用 **85 分及以上自动确认**，并要求校验通过。模型自己报出的 85% 置信度不等于平台评分，也不能通过自行抬分跳过检查。
- 失败恢复按错误类型处理：模型输出格式或映射错误允许带具体反馈修正；临时超时按退避重试；鉴权、配置或目录权限问题聚合后交给管理员。
- 为自动修正设置有限次数与总预算，建议首版每个问题最多自动修正 2 轮；成功部分复用，重启和重复点击不重复执行。
- 构建、补充回答、校验和启用使用同一持久化任务推进。浏览器关闭后流程仍继续，不让前端轮询承担发布编排。

采样开关和既有权限范围继续生效，不因简化页面而默认扩大选表范围或启用新采样。这些是本体构建阶段的规则，不改变现有 Claude 问数执行方式。

### 用户只提供必要的业务事实

适合询问：“状态值 2 表示已停用，还是已到期？现有说明不一致。”同时提供来源、选项和自由补充入口，不预选答案。回答一次后写入对应的权威定义，重新检查并继续任务。

不适合询问：“这个对象要不要 confirm？”“选择哪个 stableKey？”“是否合并第 7 个域？”“校验通过后是否再保存？”这些应由系统处理。

涉及字段与关系的问题写回数据源目录；涉及指标或业务口径的问题写回业务知识。各页面引用同一条待处理记录，避免用户重复回答。

## 5. 启用策略：推荐默认自动完成

下列为启用策略。首版已将完整构建的合并、检查、必要评测和发布移入后台；按依赖范围单独启用未完成更新中的部分内容，保留为后续增强。

- **首次构建**：用户点击“开始整理”时已明确看到“检查通过后自动用于问数”。本次选表所需对象和关系完整、没有未解决的冲突、校验通过后自动启用。
- **常规更新**：新增对象、补充可核实的描述、物理映射不变的同义名称整理，完成影响检查和必要验证后自动启用。
- **改变既有业务含义**：删除对象、变更关联路径、修改统计范围、覆盖人工定义等，先展示一份业务变化摘要，只确认这次变化，不再逐字段确认。
- **存在未解决问题**：保留现有可用版本。本轮内容继续处于更新中，不自动忽略失败表、不降低阈值、不把未完成的更新标为全部成功。
- **已有确定内容需要单独启用**：按依赖关系划分完整范围，检查其不会引用未完成对象；明确显示哪些范围尚未就绪，再提供一次“先启用已就绪范围”。这是异常处理入口，不是正常主流程的一步。

85 分只决定候选能否自动确认，不足以单独决定整批是否可用于问数。选表覆盖、依赖完整性、版本变化和必要验证仍由平台检查。缺少验证依据时保留原版本，并用业务语言指出缺口，不能让模型自生成的测试成为自己的唯一验收证据。

## 6. 从根源落地

| 改动位置 | 需要完成的工作 |
| --- | --- |
| `source-ontology-build-service.mjs` | 将现有选表到生成任务延伸到低分修正、待说明、合并、检查和启用；各阶段持久化 |
| `ontology-domain-modeling-service.mjs` | 复用已有分域执行与断点恢复，返回结构化错误类型和恢复建议 |
| `ontology-domain-draft-service.mjs` | 复用合并、目录及版本一致性检查；等价冲突自动归并，业务冲突输出具体问题 |
| `semantic-schema-service.mjs` | 复用校验和发布验证，将前端承担的评测等待迁入后台编排；版本切换前再次核对基础版本 |
| `semantic-modeling.tsx` | 当前可用结果为默认视图，移除三个并列工作模式；在对象详情中承接自然语言修正 |
| `ontology-ai-workbench.tsx` | 转为按需打开的执行详情；低分项先自动处理，仅暴露剩余业务问题 |
| 构建状态接口 | 同时返回当前生效版本、本次更新阶段、可用范围、待说明事项和可执行操作；前端不再拼多个状态猜测按钮 |

先完成后台自动衔接，再移除用户原本用于衔接流程的按钮。已有批次、审计、版本和专家编辑能力继续可追溯。旧批次保留原策略与状态，不因为新版页面或阈值变更被追溯确认。

与 2026-09-03 的 `MODELING_UI_REDESIGN_PLAN.md` 相比，本方案推进到操作流程重构。旧方案把“启动→审核→合并”视为固定主线并只调整呈现，不能满足本次尽量交给模型和系统处理的目标。

## 7. 实施与验收

第一阶段：打通后台自动衔接，提供统一状态，替换默认页面。正常构建不再进入生成工作台或版本编辑器。

第二阶段：加入有限轮数的模型自修正、自然语言补充与集中问题处理，统一目录和知识的待说明入口。

第三阶段：完善变化摘要、更新记录、按依赖划分的部分启用和恢复能力。

首版验收以操作任务为准：

1. 新用户不需要理解业务域、候选、Schema 和校准，选表后一次开始即可等待可用结果。
2. 正常构建不要求逐项确认、不要求手动合并或打开版本编辑器。
3. 进入页面可以直接判断当前能否问数，以及有没有事情需要自己处理。
4. 低分项先由模型补证据与修正；同一个业务歧义只出现一次，回答后能继续原任务。
5. 多个批次同因失败只显示一条主问题；恢复只重做必要部分，刷新和重启不会重复发布。
6. 新更新失败不会覆盖可用版本；缺表、缺对象、未解决冲突不能被隐藏成成功。
7. 模型修改不了管理员权限、自动确认分数或任务预算；专家仍能找到完整证据和恢复入口。

## 8. 首版实施记录

- 新构建由同一个持久化任务完成探查、生成、修正、合并、影响检查、必要评测和启用。页面只读取统一状态，关闭浏览器不影响后续步骤。
- 当前可用版本与本轮进度独立返回。默认结果只展示已用于问数的定义；旧生成任务不会自动变成待确认事项或追溯启用。
- 85 分阈值及确定性校验继续生效。低分或缺失对象先修正最多 2 轮，补充新业务说明后最多增加 2 轮；整次更新共用 20 轮修正额度。次数在调用前保存，刷新或普通重试不能清零。
- 临时错误和输出错误最多自动重试 2 次，已成功业务域复用；鉴权、权限、配置错误聚合后提示管理员处理。模型输出、修正与评分事件可从执行详情追溯。
- 增量更新只重新生成受结构或知识变化影响的业务域。合并保留既有名称、说明、属性与人工修正，新增字段补入；主键、类型或关系变化形成集中问题。新增数据记录且结构未变时不生成新版本。
- 合并草稿与任务检查点在同一事务中保存。切换版本再次核对原有版本；恢复任务识别已完成的发布，避免重复版本和重复发布记录。
- 结果页可搜索、展开字段、修改对象或字段的业务说明；直接修改后自动检查并生成新版本。待说明项保存为同数据源业务知识，重新评分并继续原任务。
- 本体结果不再有三个并列工作模式。更新记录、按任务展开的执行详情、版本比较与恢复、专家编辑保留在“更多”中。原有目录级关系与枚举维护仍在对应外层页签。
- 不自动启用有失败域、缺表、未覆盖对象或未解决问题的部分结果。当前版本继续保留；按依赖选择部分启用、将所有目录问答自动归并为业务问答，是后续增强项。
- 未修改 Claude 问数执行方式、SQL 次数、85 分配置、采样开关及其他模型设置。

验证：完整后端回归 599/599，通过首次自动启用、无变化复用、新增表继承人工定义、低分修正与补充后续跑、失败重试、合并事务中断恢复、发布幂等、版本绑定评测、接口身份和摘要校验；服务端渲染测试 1/1 通过。页面构建和修改文件 lint 通过。本轮未调用真实模型生成生产本体。

## 10. 三个页面的内容重构（2026-09-07）

用户指出上一版仅改变入口，进入详情后仍有旧的审核台和版本编辑器。本次直接替换旧页面内部工作流，并将三个入口一直显示在本体工作区：

| 页面 | 用户能完成的事 | 已移除的页面操作链 |
| --- | --- | --- |
| 本体结果 | 搜索对象和字段，在原位置修改业务名称与说明，保存后后台检查并启用 | 跳入结构化/JSON 编辑器、新建草稿、手动校验和发布 |
| 执行记录 | 按一次更新查看状态、阶段、问题、数据范围，展开查看模型输入和输出 | 人工审核队列、逐候选确认/合并、校准标注、全域发布单、预览和应用草稿 |
| 版本记录 | 选择版本立即查看与当前版本的变化、修改前后说明和完整定义，检查后恢复 | 手动选择比较基线、版本编辑模式切换、逐个启动发布评测 |

结果和版本共用业务定义阅读组件，历史版本只读；当前说明修改仍通过持久化后台任务完成。原始模型调用仍按 editor 权限读取。旧记录和旧草稿保留，不会因页面升级被追认或自动发布。

新增只读接口 `GET /api/sources/:sourceId/ontology-build/records/:taskId`，由服务端校验数据源与任务归属，按任务筛选模型调用；不再先取全源最近 500 个批次再过滤，避免较早更新丢失调用记录。响应只包含页面需要的进展和调用摘要，原始输入输出按需读取。

实测修复：说明修改过去将整个目录误当成此次更新范围。当现有本体只覆盖部分目录表时，保存会被要求补齐其他表。现在新任务以及旧任务恢复检查都以其基准版本的映射范围为准，目录选表不会被修改。

验证：本地浏览器已完成对象说明保存、自动启用、执行记录跳转、版本比较与恢复，检查了版本布局。构建契约 15 项通过，包含目录范围大于本体范围，以及超过 500 条无关调用时仍完整返回指定更新的回归。
