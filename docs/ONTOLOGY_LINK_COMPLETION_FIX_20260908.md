# 关系定义重复提示与补齐流程修复（2026-09-08）

## 线上证据

用户完成上一批对象审核后，同一任务显示 123 项。只读核查确认：25 次对象确认均已持久保存，对应候选全部为 confirmed。新增问题包含 53 项 Link 候选审核，以及 70 项“已确认关系尚未形成业务定义”；后者与前者重叠 53 条，真正没有候选定义的是 17 条。

210 条已确认物理关系中，140 条由已接受定义覆盖，53 条已有待审核定义，17 条漏生成。17 条分布于三个批次，分别漏 5、10、2 条。其中漏 10 条的批次有三次 `ONTOLOGY_LINK_RELATION_NOT_ALLOWED` 输出归一化错误，其他缺项不能据此推断为业务知识缺失。已发布 id 12 / v11 保留。

## 原因与修改

1. 原覆盖检查只计算已接受定义，随后将全部未覆盖关系转为补说明问题，因此待审核候选被重复计算。现在已有待审核或结构错误候选由其对应问题处理，剩余漏项合并为一个系统补齐任务。
2. 对象阶段已消耗共用的 20 次修正额度，关系补齐阶段无法重试。现在关系补齐使用独立有限额度，并先补缺项，再处理新生成候选的语义修正。
3. 原恢复逻辑在发现任意 Link 待审核时立即返回，不能独立补齐漏项。现在对象就绪后可继续补齐关系，已有 Link 审核不阻塞该操作。
4. 补缺项时以全部已有 Link 候选作为已生成范围，保留其内容和审核记录，即使模型重复返回已存在候选也不会覆盖。已确认候选仍沿用原来的状态保护。
5. 界面分开显示“系统补齐任务”和“关系定义需要审核”，并说明对象审核已保存。系统补齐支持一次操作重试，不要求逐条编写业务说明。历史 123 项在读取时直接转换为 53 项候选审核和一个包含 17 条漏项的系统任务，不改写原任务或发起模型调用。

每个关系批次初始最多修正两次（已有业务说明按原规则最多增加两次），关系阶段合计最多 20 次。用户可显式追加最多两轮重试，每轮最多增加每批两次、阶段总额度 20 次。额度在网络调用前持久保存，耗尽后显示执行问题，不能通过反复恢复任务无限调用模型。新生成内容仍需通过结构校验和原 85 分规则，漏生成不代表已确认或已发布。
