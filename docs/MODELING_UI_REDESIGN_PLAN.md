# 重设计方案：业务对象建模页面

- **日期**：2026-09-03
- **状态**：方案评审（尚未实施）
- **背景**：2026-09-03 全域建模因 `ONTOLOGY_AI_AUDIT_DIR` 落到只读文件系统而 30 域全挂（已修复，commit `cc850e4`）。事故暴露的不只是配置缺口——**页面把 30 条相同的底层错误逐域平铺**，用户完全无法判断"是我操作错了还是系统坏了"。本方案以这次事故为镜子，重新设计页面的信息架构。

---

## 1. 现状问题清单（按伤害排序）

### P0：错误呈现无诊断价值
- 30 个域失败 → 页面顶部一大段红字，同一句 `ENOENT: no such file or directory, mkdir '/app/.data'` 重复 30 遍。
- 用户读不出：这是**一个**环境问题，不是 30 个数据问题;该找运维，不是重试或改选表。
- "操作未完成""状态更新""执行失败"三个提示条同时出现，互相重复又互相稀释。

### P1：入口过多，主路径不清
- 页面头部有「AI 生成草稿 / 版本编辑器」切换，步骤条有「启动建模 → 集中审核 → 合并草稿」，面板里又有「开始全域建模」大按钮 + 「高级操作：仅重新建域，或手动指定单个域/物理范围」折叠区。
- 新用户第一眼有 4 个可点的"开始"，不知道哪个是主线。实际主线只有一条：**开始全域建模 → 审核 → 合并草稿**。

### P2：失败后的恢复路径没讲清楚
- 后端已支持 `orchestrationId` 断点续跑（成功的域自动跳过、只补失败域），但 UI 只有一个"重试"按钮，用户以为要全部重来 30 个域。
- "重试失败域 / 跳过失败域生成部分草稿 / 无损重建草稿"三种恢复动作散在不同状态下出现，没有一个统一的"出错了怎么办"面板。

### P3：进行中状态感知弱
- 全域建模一跑几分钟，30 个域串行。当前只有一行 `currentStep` + 一个百分比，看不到哪些域完成、哪些在排队、哪些失败。
- 用户中途刷新/离开页面后回来，难以快速重建上下文。

---

## 2. 设计原则

1. **一条主线**：页面只保留一条可见主路径（全域建模三步），其余入口全部收进"高级"。
2. **错误先归因再展示**：相同 root cause 的失败聚合为一条；系统性错误（环境/配置/LLM 不可达）与数据性错误（某表结构问题）分类展示，给出"该找谁"的提示。
3. **恢复动作跟着状态走**：任何失败状态下，页面明确给出下一步动作（且只给当下有效的动作）。
4. **进度可回读**：进行中/完成后都能看到逐域的状态矩阵，刷新不丢上下文。

---

## 3. 新信息架构

### 3.1 页面骨架（三段式）

```
┌──────────────────────────────────────────────────┐
│ ① 状态横幅（唯一的一条，代替现在三条提示）           │
│    - 空闲：显示"开始全域建模"主 CTA                 │
│    - 进行中：进度 + 域矩阵入口                      │
│    - 完成：成功摘要 + "进入审核" CTA                │
│    - 失败：聚合错误卡（见 3.2）                     │
├──────────────────────────────────────────────────┤
│ ② 域状态矩阵（进行中/完成后常驻）                    │
│    30 个域一格一域：✓成功 ●进行中 ○排队 ✕失败      │
│    点击失败域 → 展开该域错误详情                    │
├──────────────────────────────────────────────────┤
│ ③ 高级操作（折叠，默认收起）                        │
│    - 仅重新划分业务域                              │
│    - 手动指定单域/物理表范围建模                    │
│    - 版本编辑器入口                                │
└──────────────────────────────────────────────────┘
```

### 3.2 错误聚合卡（本次事故的直接对策）

失败时不再逐域平铺，改为按 error message 聚类：

```
┌────────────────────────────────────────────────┐
│ ✕ 全域建模失败：30/30 个域                       │
│                                                │
│ ▸ 30 个域都因同一原因失败（系统性问题）：          │
│   「服务器审计目录不可写 (ENOENT /app/.data)」    │
│   这是环境/配置问题，与所选表无关 → 请联系管理员    │
│                                                │
│ [复制诊断信息]  [修复后重试全部]                  │
└────────────────────────────────────────────────┘
```

聚类规则（前端实现，无需后端改动）：
- 对 `result.domains[].error` 做规范化（去掉域名/表名等变量部分）后分组；
- 一组覆盖 ≥80% 失败域 → 判定"系统性问题"，展示一条 + 折叠明细；
- 已知错误模式映射到人话与去向：
  | 错误模式 | 归因 | 提示 |
  |---|---|---|
  | `ENOENT`/`EACCES`/`EROFS` | 环境 | 服务器文件系统问题，联系管理员 |
  | `LLM`/`超时`/`429`/`鉴权` | LLM 配置 | 检查设置中心的模型配置 |
  | `表不存在`/`A/B 级` | 数据 | 该域的表选择或分级有问题，可单域处理 |
  | 其他 | 未知 | 展示原文 + 复制诊断信息 |

### 3.3 域状态矩阵

- 网格布局，每格：域名 + 状态图标 + （完成后）Object/Link 计数。
- 失败域点击展开错误 + 「重试此域」按钮。
- 顶部汇总：`✓ 24 · ● 1 · ○ 3 · ✕ 2`。
- 数据来源：现有 `workflow`（全域发布单）接口已返回逐域 `results`，不需要新后端。

### 3.4 恢复动作规范化

失败状态下，状态横幅右侧固定出现**一个**下拉或按钮组，按优先级只显示当下有效的：
1. 全部失败（系统性）→ 「修复后重试全部」；
2. 部分失败 → 「重试失败域（N 个）」为主按钮，「跳过失败域生成部分草稿」为次按钮；
3. 草稿校验失败 → 「无损重建草稿」。

按钮文案直接带数量与后果说明（如"只会重跑失败的 2 个域，已成功的 28 个域保留"），消除"会不会全部重来"的疑虑。

## 4. 改动范围

| 层 | 文件 | 改动 |
|---|---|---|
| 前端 | `app/ontology-ai-workbench.tsx` | 主体重构：三段式骨架、错误聚合卡、域矩阵、恢复动作区 |
| 前端 | `app/semantic-modeling.tsx` | 头部瘦身：移除双模式切换的显著性，「版本编辑器」移入高级区 |
| 前端 | 样式 | 域矩阵网格、聚合错误卡样式 |
| 后端 | 无必须改动 | 聚类在前端做；`workflow` 接口已有逐域 results |
| 后端（可选） | `ontology-domain-modeling-service.mjs` | 失败 result 附加 `errorKind`（env/llm/data/unknown)，前端聚类更稳 |

**不做的事**：不改三步主流程本身（启动 → 审核 → 合并是合理的）；不改后端任务/断点续跑逻辑（已可用）；不动版本编辑器。

## 5. 实施顺序

| # | 内容 | 验收 |
|---|---|---|
| S1 | 错误聚合卡（P0） | 复现 30 域同因失败 → 页面只显示一条聚合错误 + 归因提示 |
| S2 | 域状态矩阵（P3） | 建模进行中可看到逐域状态；刷新页面状态还在 |
| S3 | 恢复动作规范化（P2） | 部分失败时主按钮为"重试失败域(N)"，文案说明保留成功域 |
| S4 | 入口收敛（P1） | 首屏只有一个主 CTA；高级操作/版本编辑器折叠 |
| S5 | （可选）后端 errorKind | 聚类命中率 >95% |
