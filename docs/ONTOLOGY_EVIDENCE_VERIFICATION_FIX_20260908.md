# 本体候选证据核验修复方案

## 原因与目标

当前低于 85 分的有效候选直接进入人工队列。评分包含表等级、Embedding 相似度、知识和模板数量，缺少模板并不代表存在业务歧义。现有 critic 仅发现明显矛盾，不能提供正向核验结论。本次增加独立的证据核验环节：自动模式中先核验、再修正，只向用户呈现有明确疑点的业务问题。显式人工审核模式保留其原有约定。

## 实施范围

1. 用服务端提供的表字段说明、已确认关系及基数、已接受对象、已验证业务知识和当前版本构造证据集合。模型必须返回明确结论及有效证据引用；“没有明显矛盾”、自报置信度、未知引用、漏项或重复结果不能作为自动通过依据。
2. 结构错误、时间依据缺失、关系类型与基数冲突等先进入有界自动修正。模型不可覆盖结构硬约束。核验失败和生成失败属于系统任务，不要求用户补写业务说明。
3. 正向核验可使低分候选自动通过，保留原评分、核验理由、证据引用和审计事件。结论绑定候选内容、目录、基础版本、接受的端点及知识版本；异步返回后重新检查，保护既有人工决定。
4. 在对象/关系人工问题形成前执行核验；恢复历史任务时同样适用。读取状态只投影现有状态，不调用模型。重复恢复复用有效结论，失败重试与自动修正均有持久化上限。
5. 页面分别呈现系统核验任务与真正的业务问题。自动核验通过的兼容定义变更合并时复用结论，避免再次逐条要求确认；发布影响检查与回归门禁继续执行。

## 验收

- 低分但证据充分的对象和关系自动进入后续构建，评分不人为抬高。
- 模型缺项、伪造引用、返回矛盾或服务失败不能自动通过，也不能变成通用业务说明问题。
- 真正的业务疑点显示具体问题、依据与已有定义；人工决定、目录变更及并发变更受到保护。
- 历史候选可继续核验，无重复确认、无限重试或重复审计。
- 对修正、持久化、恢复和页面分流进行回归，完成类型检查、Lint、构建与现有测试；在既有授权服务器部署并核验状态。

## 真实模型回归发现的交接问题

首轮真实执行补齐了 17 条漏项，并通过证据核验接受了 45 条候选；同时发现部分人工问题仍由生成/核验错误导致：核验模型误把双向关系标签当作端点名称、将内部 `hasMeaning` 标记理解为关系没有业务意义、仅凭低匹配率要求重新确认已确认关系，以及要求在同名但不同物理映射的两条路径之间二选一。

因此补充交接前检查：明确标签与自引用的行角色，向模型隐藏内部引用校验标记；不能仅凭低匹配率或多对多推翻已确认关系。对过度描述、标签和命名冲突先作一次针对性修正，仍无法解决的具体业务疑点才交给用户。这次修正按候选持久化预留机会，恢复任务不会无限重复。跨域补边遇到已有同名但不同映射时，新路径使用独立标识，旧路径保持完整。新增的交接规则重核验尚未交付的旧疑点，已有有效正向结论继续复用。

第二轮把待处理关系降到 4 条，均为系统问题。进一步对齐修正模型与核验模型看到的证据：关系生成加入真实关联列的注释、端点字段映射和核验使用的知识标识，优先携带核验引用过的业务知识，要求名称与描述同步落实修正。显式系统重试现在会提供额外的一次修正机会；最多两次，计数持久化，避免按钮只重跑检查却无法再修正。模型协议重试会带上上次校验失败的原因。

最后 4 条经真实模型修正和核验后，210 条关系全部具有已通过定义。合并时发现另一处命名问题：不同批次的两条已确认路径共用了 `institution_leader_user` 标识，自动改名逻辑却在冲突拦截之后才执行。增量合并现会保留不同物理路径并统一改名；匹配已有路径时优先使用物理映射身份，避免再次因旧名称冲突。显式人工替换模式保持原有约定。此外，处于证据核验流程中的候选修正后，即使评分已达门槛，也必须再次完成证据核验，不能用评分跳过尚未解决的疑点。
